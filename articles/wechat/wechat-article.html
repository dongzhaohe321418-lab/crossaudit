AI 科学家，不能自己给自己的作业打分

过去一年，我一直在尝试把越来越多的科研工作交给 AI。

我的研究方向是计算化学。现在，一条基于 Claude 的科研 agent 管线已经可以规划任务、生成计算文件、把作业提交到云端超算，再将每一次实验增量推送到 GitHub。算力在云端运行，数据和过程记录保存在 Git 仓库里，一项任务失败，也不至于让整个实验重新开始。

从工程角度看，AI 已经不再只是帮助研究者检索文献或润色论文。

它开始进入科学知识的生产过程本身。

类似的事情也在其他地方发生。AI Scientist 已经尝试完成提出假设、编写代码、运行实验和撰写论文的完整流程；AI co-scientist 让多个 agent 彼此辩论和修正假设；一些自动化实验室则开始让 AI 直接参与化学合成和材料发现。

生产端正在迅速成熟。

真正没有被解决的，是另一个更安静的问题：

如果 AI 开始做科研，那么谁来审它？

一、作者和审稿人不能是“双胞胎”

现有的 AI 科学家并非没有监督机制。

一些系统设置了自动审稿人，另一些系统让专门的 Reflection agent 负责寻找漏洞。表面上看，这已经很像同行评议：一个 agent 负责提出结论，另一个 agent 负责批评。

但问题在于，生成者和审计者往往来自同一个基础模型，或者至少来自同一家厂商的同一条训练管线。

这有些像让作者的双胞胎兄弟负责匿名审稿。

两个人当然可能认真地彼此批评，但他们读过相似的书，接受过相似的训练，也共享大量没有被意识到的前提。生成者没有看到的问题，审计者也可能认为根本不需要讨论。

真正危险的错误，往往不是推导过程中的明显失误，而是那个从一开始就没有被质疑的假设。

已有研究也发现，大模型评审者可能偏好由自身或同类模型生成的内容，并表现出位置偏好、冗长偏好和自我增强。

所以，监督的价值并不只是多增加一个模型。

更重要的是，引入一种不同的错误分布。

二、CrossAudit 不是一个 review skill

我为自己的科研管线搭了一套系统，叫 CrossAudit。

最容易产生的误解，是把它理解成“给科研 agent 增加一个审稿技能”。

但一个 review skill 通常只会在任务完成后给出评价：哪里不够严谨，哪里可以改进，是否建议补充实验。评价结束以后，执行端完全可以忽略这些意见。

CrossAudit 不一样。

它连接的是科研的执行端和审计端。审计结果不是一段供人参考的文字，而是决定项目下一步状态的控制信号。

执行端每完成一个实验增量，都会把结果提交到 Git。审计端随后锁定这个具体 commit，运行检查，并返回四类裁定：

  • PASS：增量被接受，进入下一阶段；
  • BLOCKED：存在硬伤，必须修订；
  • ADVISORY：记录建议，但不阻断推进；
  • ESCALATE：系统无法可靠判断，交给人类。

因此，CrossAudit 的基本结构不是“生成以后再评论一次”，而是一条循环：

执行 → 提交 → 审计 → 裁定 → 修订或放行 → 再执行。

没有审计，执行端无法知道当前结果是否足以成为下一步的基础；没有执行，审计也没有对象。

它更接近软件工程中的持续集成，或者工业系统里的质量门，而不是一个独立的审稿插件。

三、谁来审，按照什么审

CrossAudit 的第一条原则，是异源制衡。

如果生成端使用 Claude，审计端就换成另一家模型，例如 GPT 系模型。跨厂商当然不能保证审计者一定正确，但至少能够降低两端共享完全相同盲区的概率。

第二条原则，是 Git 作为账本。

实验结果是 commit，审计报告是 commit，修订、异议和人工裁决也都是 commit。审计依据哪一版规则、哪一个数据版本，都可以通过哈希找到。

我后来意识到，Git 真正适合审计的地方，并不只是它能保存文件。

它保存的是责任。

文件可以修改，但修改无法假装从未发生。只要历史还在，任何第三方都可以重新检查当时的数据、规则和判断。

第三条原则，是确定性优先。

在任何大模型开口以前，一组纯脚本先检查数据结构、单位、来源和收敛状态。字段缺失就是缺失，量纲不对就是不对，计算未收敛就是未收敛。

这些脚本没有“智能”，也正因如此，它们的错误模式和大模型不相同。

跨厂商可以减少模型各自的偏差，却无法避免两家模型一起继承同一条错误知识。脚本不会阅读文献，也不会被一段流畅的解释说服。

因此，确定性检查的结论不能被任何 LLM 推翻。

四、怎样避免两个 AI 无限修改

只要把执行和审计接成循环，另一个问题就会出现。

如果生成者和审计者都想把结果做到尽善尽美，它们会不会不断修改，最后项目一直停留在审计阶段？

如果没有停止条件，答案是会。

生成者修正一个问题，审计者又提出一个更细的问题；每一轮看起来都更完善，整个项目却始终没有向前推进。这是一种典型的 livelock：系统一直在活动，但没有产生有效进展。

所以 CrossAudit 的目标不能是“完美”。

完美不是一个可判定状态，也没有稳定终点。

它真正判断的是：

这个实验增量是否已经达到足以继续推进的最低标准。

因此，系统必须把“不能继续的问题”和“还能继续改进的问题”分开。

只有明确的硬伤才能被标记为 BLOCKER，例如数据矛盾、单位错误、来源缺失、计算未收敛，或者结论明显超出证据。

至于是否可以增加更多对照、图表是否还能更好、方法是否可以更优雅，只能记为 ADVISORY，不能阻断流程。

否则，任何科研结果都永远不会完成，因为它总还有继续改善的空间。

审计者也不能在过程中不断提高标准。每一个 blocker 都必须引用已经存在的规则编号，指出证据位置，并说明怎样修改才足以解除阻断。

没有规则编号的新意见，只能作为建议，或者提交给人类修改下一版规则，不能在当前审计中临时变成法律。

每一轮修订还必须产生可验证的进展：未解决的 blocker 数量应当减少，或者至少有一个 blocker 的状态发生实质变化。

如果两个 agent 围绕同一条规则反复争论，却没有增加任何新信息，继续调用模型只会产生更多文字。

因此，自动修订最多进行三轮。

三轮以后仍然无法解决，系统自动建立 GitHub Issue，把原始结果、审计报告、每一轮 diff、生成者异议和审计者理由一起交给人类。

系统必须知道什么时候继续，也必须知道什么时候承认自己无法判断。

五、阻断一个增量，不阻断整个项目

另一个极端，是某个局部争议拖住整条科研管线。

CrossAudit 阻断的单位不是整个项目，而是一个具体实验增量。

某个增量未通过审计，只暂停依赖它的下游任务。其他互不依赖的计算仍然可以继续运行。

这样，审计可以阻止错误向下传播，却不会因为追求严谨而让整个项目冻结。

人的角色也随之改变。

研究者不再逐项阅读每一次 agent 输出，而是负责制定规则、处理争议、判断不可形式化的科学价值，以及定期检查规则是否已经被系统“应试”。

监督成本不再与全部产出数量成正比，而只与异常数量相关。

六、这实际上是一种权力结构

如果把整个系统压缩成一句话，它并不是两个 AI 彼此聊天，而是一种权力分配：

执行端拥有生产权，但没有自行放行的权力；审计端拥有阻断权，但没有临时立法和无限拖延的权力；人类保留立法权和最终裁决权。

CrossAudit 不能证明一项研究必然正确，也不能代替真正的同行评议。

它更像科学声明的持续集成：在每一个实验增量进入下一阶段以前，持续检查那些已经能够被规则化的问题。

科学从来不只是生产知识。

它同样是一套怀疑知识、检查知识，并允许错误被公开修正的制度。

AI 科学家已经开始进入实验室。

它们可以提出假设，可以运行计算，也可以写出论文。

但它们不能自己给自己的作业打分。

现在，它们也不必了。
